# 老年人健康监护系统

面向社区养老场景的健康管理与医疗调度平台。系统以"社区工作人员—医生—系统管理员"三类角色为主线，覆盖老人档案、监护设备、求助告警、派医工单、巡访记录、摔倒处置、随访计划和健康评分等业务闭环。其中 **AI 辅助诊断已接入真实大模型（OpenAI 兼容接口）**，调用异常时自动回退到规则引擎，保证功能可用。

## 需求背景

我国人口老龄化程度持续加深，越来越多的老年人选择居家或社区养老。社区工作人员需要同时掌握辖区内老人的健康状况、监护设备、医生资源和应急事件；一旦老人发生摔倒、突发不适或主动呼救，能否在最短时间内发现、派单、上门处置，直接关系到老人的生命安全。

传统社区养老管理多依赖纸质档案、电话通知和微信群调度，普遍存在以下痛点：

- 老人信息分散在多份表格中，病史、用药、紧急联系人难以快速调取；
- 跌倒监测、SOS 设备告警与派医流程脱节，容易出现漏接、漏派、响应不及时；
- 工单靠电话口头传达，谁接收、谁上门、处理到哪一步缺乏统一跟踪；
- 医生上门巡访后记录零散，体征数据和处置结果无法沉淀、无法追溯；
- 社区缺少对老人健康变化的整体评估手段，重点老人难以提前识别；
- 慢性病老人需要定期随访，但随访计划靠人工记忆，容易遗漏。

本系统正是针对上述场景设计，用一套线上化流程把 **老人档案 → 监护设备 → 求助告警 → 派医工单 → 上门巡访/应急处置 → 健康评估 → 随访计划** 串联起来，让社区养老的日常监护和应急调度有据可查、有流程可依。

## 解决的核心问题

| 痛点 | 系统提供的解决方式 |
| --- | --- |
| 档案分散、调取困难 | 统一老人档案，记录基本信息、既往病史、过敏史、用药、紧急联系人，按社区隔离管理 |
| 告警响应慢、易漏派 | 设备触发告警后自动生成求助事件与派医工单，进入统一的派单队列 |
| 派医过程不透明 | 工单从"待分配医生"到"已完成"全状态留痕，社区可实时掌握进度 |
| 巡访记录难沉淀 | 医生上门后结构化填写体征、身体状态、用药、主观症状和处置结果 |
| 健康状况难评估 | 根据年龄、慢性病、血压、心率、血糖自动生成健康评分与等级 |
| 随访靠人工记忆 | 社区可建立周期巡访/健康随访计划，维护周期与下次随访日期 |

## 系统定位与使用角色

本系统服务于"社区—医生—管理者"三端协同：

| 角色 | 在业务中的职责 |
| --- | --- |
| 社区工作人员 | 维护老人档案、医生与监护设备；创建/接收工单并派单；跟踪巡访记录与求助事件；制定随访计划 |
| 医生 | 接收本人工单，上门巡访或处置设备告警；回填巡访记录或摔倒处置记录；使用 AI 辅助诊断 |
| 系统管理员 | 维护全量基础数据（社区、用户账号、社区人员及各业务表），负责数据层面的增删改查 |

一个社区可有多名工作人员和多名医生；每位医生归属一个社区；社区工作人员只能看到本社区数据，医生只能看到指派给自己的工单和自己负责的老人。

## 一次完整业务闭环（以摔倒告警为例）

1. 老人在家摔倒，佩戴的跌倒监测设备触发告警（演示环境中由社区人员在"监护设备"页模拟触发）。
2. 系统生成一条"求助事件"，并自动创建一张状态为"待分配医生"的工单。
3. 社区工作人员在"派医工单"中把工单派给本社区医生，事件状态变为"已派单"。
4. 医生在"我的工单"中接收工单，状态变为"进行中"；出发巡访时点击开始，状态变为"巡访中"。
5. 医生上门后在"摔倒处置"中填写现场情况、受伤部位、伤情程度、生命体征、处置措施和是否送医。
6. 提交后工单变为"已完成"，关联事件变为"已处理"；本次体征数据同时成为该老人健康评分的计算依据。
7. 社区可在"巡访记录/求助事件"中回溯全过程，并根据情况为该老人建立后续随访计划。

普通巡访（非设备告警）由社区直接创建工单并指派医生，医生上门后填写"巡访记录"，其余流转相同。

## 功能概览

### 社区工作人员
- **工作台**：老人档案数、在册医生数、工单总数、待办工单统计，以及待办/最近工单列表与快捷入口。
- **老年人管理**：老人档案增删改查，查看健康评分与巡访、处置记录。
- **医生管理**：本社区医生信息维护。
- **派医工单**：创建巡访工单、为"待分配医生"工单派单、跟踪工单状态。
- **巡访记录**：查看本社区老人的巡访记录。
- **监护设备**：跌倒监测/SOS 设备的绑定、状态维护，支持模拟触发告警。
- **求助事件**：查看设备告警事件及处理状态。
- **随访计划**：创建周期巡访/健康随访计划，维护下次随访日期与状态。

### 医生
- **我的工单**：接收、开始巡访、退回工单；对设备告警工单填写摔倒/紧急处置记录，对普通工单填写巡访记录。
- **老人档案**：查看负责老人的档案，并维护现病史、用药情况、身体现状。
- **我的巡访记录**：查看本人提交的巡访记录。
- **AI 辅助诊断**：接入真实大模型，根据老人档案、体征与症状生成诊断提示和处置建议；模型异常时自动回退规则引擎。

### 系统管理员
- **数据管理后台**：对老人、医生、工单、巡访、摔倒处置、设备、事件、随访、社区、社区人员、用户账号共 11 张表做通用增删改查。
- **级联删除**：删除老人/账号/社区等主数据时，按外键依赖顺序自动清理关联数据。
- **账号安全限制**：不允许删除当前登录的管理员账号。

## 核心业务流程

### 关键业务对象关系

```
监护设备 device ──绑定──► 老人档案 elderly
      │                        │
   触发告警                 健康评分 / 随访计划
      ▼                        ▲
求助事件 help_event ──自动生成──► 派医工单 order_form
                                     │ 医生上门处置
                    ┌────────────────┴────────────────┐
                    ▼                                 ▼
            巡访记录 visit_record            摔倒处置记录 fall_record
                    │                                 │
                    └──────► 回写工单 / 事件状态 ◄──────┘
```

### 工单状态流转

```
社区创建工单 ──────────────► 待接收
设备告警自动生成 ──► 待分配医生 ──派单──► 待接收
                                          │ 医生接收
                                          ▼
                                       进行中
                                          │ 医生开始巡访
                                          ▼
                                       巡访中
                                          │ 提交巡访记录 / 摔倒处置记录
                                          ▼
                                       已完成

医生可随时将本人工单退回 ──► 已退回
```

- 设备触发告警时，系统自动创建一条"待分配医生"工单，并把事件置为"待处理"。
- 工单派单成功后，关联事件状态变为"已派单"。
- 医生提交巡访/处置记录后，工单变为"已完成"，关联事件变为"已处理"。

### 健康评分

依据老人档案与**最近一次巡访记录**自动计算，包含五项：

| 维度 | 说明 |
| --- | --- |
| 年龄 | 按年龄段计分 |
| 既往病史 | 按慢性病数量扣分 |
| 血压 | 按收缩压/舒张压分级计分 |
| 心率 | 按静息心率区间计分 |
| 血糖 | 按空腹血糖区间计分 |

结果同时输出各维度得分明细、依据说明与等级（优 / 良好 / 一般 / 较差 / 需关注）。无巡访记录时显示"暂无巡访记录"。

### AI 辅助诊断（真实大模型 + 规则兜底）

系统优先调用真实大模型完成辅助诊断，调用失败或未配置密钥时自动回退到内置规则引擎，页面会标注结果来源（"大模型生成"/"规则兜底"）。

调用流程：

1. 前端提交所选老人 `elderlyId`、本次体征（血压/心率/血糖）、身体状态和主观症状；
2. 后端读取该老人的年龄、性别、既往病史、过敏史、现病史、用药情况、身体现状，以及最近一次巡访体征；
3. 将这些信息组装为提示词，通过 OpenAI 兼容接口 `POST {base-url}/chat/completions` 调用模型；
4. 要求模型返回严格 JSON：`diagnosis`（初步分析）、`advice`（分条建议）、`confidence`（置信度）、`riskLevel`（低/中/高/危急）；
5. 解析失败、超时、网络异常或额度不足时，回退到规则引擎并返回 `source=rule`。

相关配置位于 `backend/src/main/resources/application.properties`：

| 配置项 | 说明 |
| --- | --- |
| `ai.enabled` | 是否启用大模型，默认 `true` |
| `ai.api-key` | 模型密钥，建议通过环境变量 `AI_API_KEY` 注入，不要提交到仓库 |
| `ai.base-url` | OpenAI 兼容接口地址 |
| `ai.model` | 模型名称 |
| `ai.timeout-seconds` | 请求超时，默认 20 秒 |
| `ai.temperature` | 生成温度，默认 0.3 |

可直接使用的免费方案：

| 服务 | `base-url` | `model` | 说明 |
| --- | --- | --- | --- |
| 智谱 GLM-4-Flash（默认） | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` | 到智谱开放平台注册后获取免费 API Key |
| 硅基流动 SiliconFlow | `https://api.siliconflow.cn/v1` | `Qwen/Qwen2.5-7B-Instruct` | 注册后有免费模型额度 |
| 本地 Ollama | `http://localhost:11434/v1` | `qwen2.5:7b` | 数据不出内网，`ai.api-key` 填任意值（如 `ollama`） |

配置密钥（最简单的方式）：

打开 `backend/src/main/resources/application-local.properties`，把密钥粘贴到 `ai.api-key=` 后面，保存并重启后端即可。该文件已被 `.gitignore` 排除，不会上传到仓库；也支持通过环境变量 `AI_API_KEY` 注入。

> AI 输出仅作辅助参考，不能替代医生诊断；接入真实模型后，`/api/ai/**` 已改为登录后可用，避免接口额度被匿名调用。

## 快速开始

### 环境要求

- JDK 17+
- Maven 3.8+
- Node.js 18+
- MySQL 8.x

### 1. 初始化数据库

```bash
# 在 MySQL 中执行建库、建表与演示数据脚本
mysql -u root -p < sql/schema.sql
```

脚本会创建数据库 `elderly_care_system`，并写入 4 个社区、9 位老人、4 位医生、6 台设备及若干工单/巡访/事件/随访演示数据。

> 注意：默认配置连接 `localhost:3307`。若本机 MySQL 使用 3306，请修改 `backend/src/main/resources/application.properties` 中的数据源配置。

### 2. 启动后端

```bash
cd backend
mvn spring-boot:run
```

- 服务端口：`8080`
- 上下文路径：`/elderly-care-system`
- 接口根地址：`http://localhost:8080/elderly-care-system/api`

### 3. 启动前端

```bash
cd frontend-vue
npm install
npm run dev
```

- 访问地址：`http://localhost:5173`
- Vite 已将 `/api` 代理到后端 `http://localhost:8080/elderly-care-system`
- 路由采用 Hash 模式，例如 `http://localhost:5173/#/login`

| 后台 | `GET/POST/PUT/DELETE /api/admin/?table=` | 通用数据管理（仅管理员） |

## 数据库表

| 表名 | 说明 |
| --- | --- |
| `user` | 系统用户（社区人员、医生、管理员） |
| `community` | 社区信息 |
| `elderly` | 老人档案（含现病史、用药、身体现状） |
| `doctor` | 医生信息，关联用户与所属社区 |
| `device` | 监护设备（跌倒监测 / SOS 求助） |
| `help_event` | 求助事件（摔倒告警 / 手动呼救） |
| `order_form` | 派医工单 |
| `visit_record` | 巡访记录（含体征与 AI 建议） |
| `fall_record` | 摔倒/紧急处置记录 |
| `community_staff` | 社区工作人员任职（一人一社区） |
| `follow_up_plan` | 随访计划 |

## 权限与数据隔离

- **社区工作人员**：只能查看和操作**本社区**的老人、医生、设备、工单、巡访、事件与随访计划。
- **医生**：只能处理**指派给自己**的工单，只能维护**自己负责的**老人健康字段。
- **系统管理员**：仅可访问 `/api/admin` 数据管理接口，不能调用业务接口；不能删除当前登录账号。
- **未登录**：除登录接口外，一律返回 `401`（AI 诊断接口也需要登录）。

## 说明

- 本系统为课程/演示项目，账号密码以**明文**存储，生产环境需改为加密存储并接入更严格的认证方案。
- 会话超时时间为 30 分钟；前端将 `sessionId` 存入 `sessionStorage`，并通过 URL 重写 `;jsessionid=` 兼容代理场景下的会话传递。
- 前端使用 Hash 路由，刷新页面不会丢失当前路由。
- AI 诊断优先调用大模型，未配置密钥或调用失败时回退到规则引擎，结果会标注来源；输出仅作辅助参考，不能替代医生判断。
